# 好友与整合包邀请：首版设计提案

设计日期：2026-10-23。执行状态（2026-10-24）：用户随后以“run”授权实现，账号、双向好友、指定版本卡片和本机双客户端已实现；公共服务未部署。实测范围和外部发布条件见 [好友验证记录](../../verification/friends-results.md)。

用户要求：为现有原版直达工具自行设计添加好友功能。下文保留设计时的方案与边界；具体实现按后续执行计划推进，不把本机验证等同于公网可用。

## 1. 产品判断

原版直达的价值是让普通玩家方便安装、继续使用 PCL。好友功能的首个用途定为：两名认识的玩家互相添加，然后向对方发送准确版本的整合包安装卡片，减少反复描述包名和装错版本。

这项用途是待验证假设，现有对话没有证明玩家需要在安装器里聊天或长期维持社交关系。衡量价值时观察双向添加后有没有实际发送、接收和完成预检；如果只发生一次性分享，后续优先提供免好友的分享方案，而不是继续扩大社交系统。

成功场景：甲发好友码给乙 → 乙核对昵称和完整好友码并申请 → 甲同意 → 甲分享选定的整合包版本 → 乙查看来源和预检 → 自主安装 → 回到 PCL 选择新实例。

## 2. 方案比较与推荐

| 方案 | 获得什么 | 成本与不足 |
| --- | --- | --- |
| 本地联系人与复制分享内容 | 没有服务端也能记朋友、转发项目信息 | 不是跨设备双向好友，不能收到对方申请或确认 |
| 双向好友＋整合包卡片（推荐） | 真正好友关系、接收申请、指定包版本的收件箱 | 需要账号、持续运行的服务端、数据库、邮件发送与维护 |
| 聊天、在线状态、语音与直接联机 | 更完整的社交与联机体验 | 引入消息运维、状态同步和联机基础设施，当前安装器无法直接提供这些能力 |

用户把设计决策交给我们，因此本提案选择第二项。它与已有整合包能力关联最直接；第三项暂不进入首版。仅为节省后端而把本地联系人标成“好友已添加”会误导玩家，不采用。

## 3. 首版范围

### 必须有

- 独立、可选的原版直达账号；不用好友时原版安装与整合包检索保持无需账号。
- 我的好友码、复制按钮；输入好友码后核对资料并申请，收到者同意后才成为双方好友。
- 申请列表：收到的同意/拒绝，发出的撤回；双方列表与服务端状态一致。
- 好友列表、仅本机备注、删除好友、拉黑和解除拉黑。
- 向已确认好友发送指定版本的 Modrinth 整合包卡片，以及接收、查看、忽略、转入现有预检流程。
- 服务不可用、未登录、申请处理中、已是好友、已拉黑、邀请已过期、包版本失效等明确状态。

### 暂不包含

- 自由聊天、语音、动态、公开广场、按昵称搜索陌生人、好友推荐。
- 在线/离线状态、正在玩的游戏或实例识别、读取 PCL/Xbox 好友。
- NAT 穿透、服务器托管、自动加入游戏、一键联机承诺。
- 上传整合包归档、私有包、任意下载链接、存档、配置、模组文件或远程执行命令。

## 4. 账号与身份

- 首次进入好友功能显示“启用好友”，说明会连接好友服务；仅此时注册/登录，首次启动安装器不弹注册框。
- 账号采用邮箱、密码与昵称；昵称允许重复，不作为唯一身份。邮箱验证后启用申请和发送卡片。登录、验证和找回密码复用 ASP.NET Core Identity 的标准能力；不得把昵称塞入框架要求的 Email 字段绕过约束。
- 使用原版直达自己的身份，不要求或接触 PCL/Microsoft/Minecraft 密码、令牌与正版资格。邮箱仅本人和身份服务可见，不给好友接口返回。
- 服务端随机分配 12 位易读好友码，分三组显示，查重后保存。好友码是公开查找标识，不能作为登录、重置密码或自动同意的凭据。
- 用户 ID 永久稳定；好友码可主动重置，旧码立即失效，已建立的关系不受影响。账号支持修改密码、退出所有设备、删除账号。
- 本机“记住登录”可选；使用 Windows 当前用户保护存储，不明文落地密码或令牌。退出时删除本地凭据，服务端撤销会话；每个受保护接口校验撤销状态，重放已撤销的访问和刷新凭据必须失败。

## 5. 添加好友流程与关系规则

1. 输入好友码，允许粘贴、自动忽略分隔符和大小写差异；不支持模糊匹配或列举用户。
2. 通过精确码查看最小资料：昵称、完整好友码、系统首字占位头像。无已验证头像来源前不加载 MC 皮肤或生成头像。
3. 点“发送申请”，显示“等待对方同意”；这里不显示“添加成功”。收到者看到同样的最小资料，核对后同意或拒绝。
4. 同意时服务端事务创建唯一无方向好友关系，双方刷新后可见。重复点击和网络重试幂等；交叉申请不会自动成为好友，可明确同意已有申请。
5. 请求默认 7 天过期。相同方向的待处理申请只保留一份；拒绝/撤回后 24 小时内不允许对同一用户再次发送。
6. 无效码、不可申请账号和被对方拉黑对申请者统一提示“暂时无法向该好友码发送申请”，不泄露拉黑状态。自己的码与已是好友可给出具体提示。
7. 删除好友需确认，双方关系解除，旧待处理邀请失效；不向对方自动发送通知。拉黑同时删除关系、撤销双方待处理申请/卡片，并阻止双向新交互。解除拉黑不恢复关系或旧邀请。
8. 本机备注不上传，不冒充对方昵称。更名时显示最新昵称，完整好友码与稳定 ID 保持核对依据。

## 6. 整合包邀请：准确且不代替用户做安装决定

- 发送入口放在已选定可支持包版本的整合包页，以及好友详情的“发送整合包”。选择好友和版本后先显示发送预览；无精确版本不能发送。
- 首版仅发送现有支持范围内的 Modrinth Fabric、MC 原版正式版整合包。服务端保存结构化的来源 `modrinth`、`projectId`、`versionId`，不接受发送者指定下载 URL、脚本、文件路径或富文本说明。
- 同时保存来源元数据中所选 `.mrpack` 的 SHA-512，服务端核对散列属于该版本的文件。接收端按相同散列定位归档并沿用既有散列校验；找不到原归档就提示失效，不因同版本存在多个文件而任意换用另一个。
- 接收端重新从 Modrinth 获取精确 versionId，并校验它属于 projectId、项目类型为整合包、加载器与 MC 范围受支持。标题、图标和简介继续使用来源数据并标来源；好友无法伪造“官方介绍”。
- 服务端在发送时也核对上述元数据，防止客户端绕过界面；接收端校验仍保留。来源不可用则提示重试，不凭发送者填的文字放行。
- 只有服务端成功保存才能显示“已发送”；没有读取回执就不显示“已读/对方已看到”，不把客户端提交成功当作对方接收成功。
- 收到卡片只显示“查看并检查”，不自动下载文件或安装。该按钮由用户主动触发精确版本下载与现有 mrpack 预检；保留目录确认、可选项选择、新实例名称与最终“开始安装”。
- 版本404、删除、隐藏或已不支持时卡片显示无法获取，不偷偷改装最新版本。邀请状态以好友服务为准；删除/拉黑/撤回/7天过期后不能开始新的预检。
- 首版不跨电脑传可选文件选择或自定义本地改动。文案只说“同一发布版本”，不保证双方模组目录、配置和服务器兼容性完全相同。
- 完成页只对接收者报告本地安装结果；不把目录、存档或本机安装状态上传给发送者。好友关系解除不会撤销已经完成预检后由用户发起的本地安装；不允许好友远程取消或控制本机任务。

## 7. 页面与交互

- 主导航新增“好友”，沿用 WPF 浅色、蓝色重点、现有字体和 Styles.xaml 色值；好友页不要求确认游戏目录。实际安装仍须回到共享目录区确认。
- 顶部为我的昵称与好友码（复制）、“添加好友”和账号菜单；中部为“好友 / 申请 / 整合包邀请”三个简单列表。
- 700×800 默认尺寸用单列表＋详情窗口，560×580 最小尺寸保持单列与滚动，不强行塞双栏。好友行显示昵称、本机备注与明确的“查看”按钮，不放未经验证的在线绿点。
- “添加好友”原生窗口只有好友码、核对结果、发送申请/取消。回车提交、Esc关闭、Tab可达，异步按钮防重入，错误在输入附近显示，返回不丢输入。
- 空列表：“还没有好友。复制你的好友码发给朋友，或输入朋友的好友码。”没有模拟联系人、虚构在线人数或自动邀请。
- 断网显示“好友服务暂时无法连接，显示上次同步的名单”，缓存与时间戳明确；增删操作不在离线时假装成功。缓存仅登录用户本机可见，退出后清除。
- 首版进入好友页同步，页面可见且窗口活动时每30秒刷新；切后台/离开页暂停，手动刷新可用。离线请求留服务端，重新打开后接收，不承诺桌面后台推送。
- 现有安装期间禁止切换主页面的保护先保留；好友任务不拿 InstallationGate。收到安装邀请时只把验证后的输入交给整合包预检，真正安装复用同一把锁。

## 8. 架构和运营边界

当前仓库只有 WPF 客户端与 Core，未发现账号、后端或好友配置，不能靠添加一个按钮完成真实跨电脑好友。

推荐单体 .NET 10 ASP.NET Core 好友 API，复用同一语言与 Identity；小规模部署先用 EF Core＋SQLite 的单实例持久化数据库，数据文件和备份必须放持久卷。规模增长后再评估迁移；首版不引入 Redis、微服务或 WebSocket。

客户端计划新增 Core/Friends 下的 DTO、IFriendService 与 ViewModel，App 下原生好友页/申请窗口/邀请卡片；服务端独立项目单独部署。好友 HTTP 客户端只允许配置的 HTTPS 服务源，无跨源重定向；认证头不得复用到 Modrinth、CDN 或 Minecraft 请求。

主要实体：Identity账号及会话版本、公开资料/好友码、唯一好友关系（排序后的双方 ID）、好友申请、定向屏蔽、整合包邀请。备注留本机。服务端以认证主体决定操作者，不能相信请求体填写的 senderId。

服务端负责权限、分页、事务、唯一约束与幂等；每次读取/修改邀请都校验发送者/接收者、好友关系、屏蔽、过期状态。列表每页20项。账号删除后立即不可登录、不能被查找，事务删除关系、申请、邀请；备份保留与恢复后的删除重放见运营说明。

初始防滥用参数为设计者默认：精确码查询每账号30次/分钟，申请10次/日且待处理最多20，发送卡片30次/日，好友上限200；注册/登录另加IP限流与框架失败锁定。限制服务端实施，返回可理解的重试时间，不由客户端计数代替。

维护者需要提供服务部署位置、HTTPS域名、邮箱发送通道、数据库备份和故障联系渠道。这些均未配置，费用与地区可用性尚未验证；不默认使用付费服务，不在本轮部署或创建账号。

服务故障与停服时好友页明确不可用，现有下载和安装仍可独立使用。上线前更新隐私说明：列明邮箱、昵称、关系和邀请数据，访问日志7天、过期申请/卡片清理30天、加密备份30天的建议保留期；删除请求在备份恢复后重新执行，凭据/邮箱不进入普通请求日志。以上为拟定的数据策略，需在具体运营环境落地验证。

## 9. 分阶段交付与验收

1. 本轮：完整设计＋独立可实施性检查。尚不把设计当成已经可用的功能。
2. 开发闭环：本机隔离好友服务和两个独立客户端身份；注册/验证/登录、添加/同意/删除/拉黑、精确版本卡片与预检串通，邮件使用明确的开发测试收件箱，不伪装公网投递。
3. 发布候选：在实际服务上用两台不同电脑验证生命周期、断网恢复、邮箱投递、持久化与备份；完成安装回归后再更新公开包。

必须通过的可检查标准：

- A申请时B未同意，双方均未成为好友；B同意后刷新，两侧一致。重试、重复同意、交叉申请只有一条关系。
- 自己、错误码、重复申请、过期、拒绝、撤回、拉黑都有正确结果；第三个用户C无法读或处理A/B的申请与邀请。
- 删好友/拉黑与发送/接受并发时事务结果一致；已撤销会话不能重放；令牌不进入日志或外部来源请求。
- 包卡片精确到项目与版本，来源正文/图标不可被发送者替换；404和不支持的加载器不能自动切到其他版本；超限与异常返回可恢复。
- 没有对游戏文件的无提示写入；检查/安装遵守现有预检、目录确认、互斥锁、取消和存档保护。没有好友账号也能完成原来的操作。
- 未配置服务不显示成功或模拟好友；活动页/后台轮询行为符合设计；两种窗口尺寸与键盘操作通过实际检查。

## 10. 核查依据

- 本地 MainWindow、ModpackViewModel、InstallationGate、Styles.xaml：现有结构、目录确认、安装锁与界面规范。
- [ASP.NET Core Identity API 官方文档](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/identity-api-authorization?view=aspnetcore-10.0)：身份管理、邮箱密码接口与适合简单非浏览器客户端的令牌选项。具体撤销策略需实现并验证，不能假定清除本地文件即完成撤销。
- [Windows ProtectedData](https://learn.microsoft.com/en-us/dotnet/api/system.security.cryptography.protecteddata?view=net-10.0)：Windows用户范围保护能力。
- [Modrinth Get version](https://docs.modrinth.com/api/operations/getversion/)：精确版本ID、所属项目、文件与散列元数据。只支持现有已允许来源。
